# S8. External benchmark adapters and evidence mapping

## S8.1 General rule

For each external benchmark, the mapping identifies the proposed consequential action and the evidence connecting that action to an external effect. The benchmark defines its tasks, attacks, native defenses, model calls, memory representation, tool environment, and scoring procedure. Under that procedure, the native score measures benchmark performance. In EAL-Bench and AgentDojo, the separate authorization decision concerns the current support available immediately before the proposed action reaches the tool.

For EAL-Bench, this supplement describes the protected path and the records needed to compare it with native execution. For AgentDojo, it describes the support derived from the legitimate task. For Agent Security Bench (ASB), the supplement gives the conditions under which a record supplies primary evidence for an authorization claim. Finally, the supplement reports the independent AgentDojo scores and identifies the code and records available for each benchmark.

## S8.2 EAL-Bench

### Protected path

In the proposed EAL-Bench path, the executor first receives the frozen memory specified for the trial and uses it to propose an action. Next, the adapter resolves current authorization for that proposal. Then, it revalidates memory and checks the exact support bound to the action before the protected commit decision. At this point, the decision at protected commit determines whether the executor proposal can proceed to the native tool. From the executor input to the native tool, the proposed path is as follows.

$$
\begin{aligned}
&\text{Frozen Memory}
\rightarrow \text{Executor Proposal}
\rightarrow \text{Current Authorization Resolution} \\
&\quad \rightarrow \text{Memory Revalidation}
\rightarrow \text{Exact Support Revalidation} \\
&\quad \rightarrow \text{Protected Commit}
\rightarrow \text{Native EAL Tool}.
\end{aligned}
$$

### Coverage

For each domain, the table counts the ordinary trials specified by the registered design across cases, seeds, writers, executors, and conditions. Within each domain, the denominator counts authorized trials for a given writer under a given condition of the registered design. In the public design snapshot dated 18 September 2026, the request authorization field gives the oracle's decision, while the action field indicates whether the requested action occurred. The executor identifier names the model. For the three domains, the registered trial counts and authorized denominators are as follows.

| Domain | Cases | Seeds | Writers | Executors | Conditions | Authorized denominator/condition | Selected ordinary trials |
|---|---:|---:|---:|---:|---:|---:|---:|
| Procurement | 12 | 3 | 5 | 2 | 4 | 72 | 8,640 |
| Cybersecurity | 16 | 3 | 5 | 2 | 4 | 128 | 15,360 |
| Finance | 8 | 3 | 5 | 2 | 4 | 64 | 7,680 |
| **Total** | **36** |  |  |  |  | **264** | **31,680** |

### Important limitation

For a paired comparison, the native and protected records must identify the same request and the same frozen memory. The archived design does not contain these paired observations. For each domain, the [offline check](../Data_and_Code_Availability/S8_external_validation/eal_preflight_report.json) counts the ordinary trials specified by the cases, seeds, and model configurations in that design. Thus, the reported count describes design coverage and cannot establish how often unauthorized execution occurs on the proposed protected path.

## S8.3 AgentDojo

Before evaluating a consequential AgentDojo call, the guard uses a fixed reference set of calls authorized by the legitimate user task. Under the [reviewed tool policy](../Data_and_Code_Availability/S8_external_validation/agentdojo_tool_policy_v1.json), the guard uses the tool classifications available for four benchmark suites, namely, Banking, Workspace, Slack, and Travel. In strict mode, the guard denies unclassified tools. At the tool boundary, the guard compares the proposed function and its arguments with the entries in the fixed reference set. Thus, a prompt injection can alter the proposal, but cannot add authority to the reference set.

## S8.4 Agent Security Bench

For ASB, a case qualifies for the primary authorization analysis only when its record supports three separate checks. First, $C_1$ requires the record to establish the legitimate support relevant to the proposed consequential action. Next, $C_2$ requires evidence connecting the action influenced by the adversary to the specific operation examined for an external effect. Finally, $C_3$ requires the record to supply explicit evidence of the external effect attributable to the operation under assessment. For each case, the eligibility rule is as follows.

$$
\mathrm{Eligible}_{ASB}=C_1\land C_2\land C_3.
$$

For ASB, the [offline check](../Data_and_Code_Availability/S8_external_validation/asb_preflight_report.json) tests whether the mapping excludes a record from the primary analysis when evidence of the external effect is missing. The native checker can assign its attack outcome from messages. In particular, poisoned memory can influence the proposed action without supplying legitimate support for the agent to execute it. Thus, the synthetic check illustrates the eligibility rule and does not measure the frequency of unauthorized effects in ASB.

## S8.5 Cross-source AgentDojo threat context

In the [independent AgentDojo report](https://github.com/Forever-CodingNoob/agent-security-tools-survey/blob/69b91ef80121777591d6589752766e29d5aada4f/agentdojo/README.md), Forever-CodingNoob reported native utility and security for 949 attacked pairs per model. Across the three configurations, the evaluation covered 2,847 attacked pairs. In the independent evaluation, none of the models ran with the proposed authorization gate in place at the tool boundary. Thus, the scores describe the external threat context and do not measure authorization consistency in the controlled experiments. For each model in the independent evaluation, the native utility, native security, and corresponding attack-success complement are as follows.

| Model | Pairs | Native utility | Native security | Attack-success complement |
|---|---:|---:|---:|---:|
| qwen3:14b | 949 | 52.8% | 17.6% | 82.4% |
| qwen3-coder:30b | 949 | 36.6% | 21.9% | 78.1% |
| gpt-oss:120b | 949 | 54.9% | 27.0% | 73.0% |
