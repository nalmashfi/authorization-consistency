# S8. External benchmark adapters and evidence mapping

## S8.1 General rule

For each external benchmark, the evidence mapping identifies the point at which a proposed action can produce a consequential effect and the evidence available there. Each benchmark defines its tasks, attacks, and native defenses and controls model calls, memory representation, the tool environment, and native scoring. In benchmarks such as EAL-Bench and AgentDojo, the authorization check examines the current support for the proposed action immediately before execution. Thus, the native score and the authorization decision describe benchmark performance and the authority to execute the proposed action, respectively.

The EAL-Bench section introduces the protected path and identifies the trial records missing from the comparison of the native and protected conditions. The AgentDojo section reviews how the guard uses support derived from the legitimate user task to assess a consequential tool call. Next, the Agent Security Bench (ASB) section gives the conditions for including a case in the primary authorization analysis. The cross-source section presents the independent AgentDojo results. Finally, the file index summarizes the available code and records by benchmark.

## S8.2 EAL-Bench

### Protected path

In EAL-Bench, the protected path connects the executor proposal to the native EAL tool through a sequence of authorization checks. First, the executor receives the frozen memory, uses it to select an action, and then proposes that action to the native tool environment. Next, the adapter resolves current authorization for the proposed action. Then, the adapter revalidates both the memory used by the executor and the exact support for the action. Afterward, the action reaches protected commit. Finally, the native tool produces the effect. From the frozen memory to the native tool effect, the checks and operations are as follows.

$$
\begin{aligned}
&\text{Frozen Memory}
\rightarrow \text{Executor Proposal}
\rightarrow \text{Current Authorization Resolution} \\
&\quad \rightarrow \text{Memory Revalidation}
\rightarrow \text{Exact Support Revalidation} \\
&\quad \rightarrow \text{Protected Commit}
\rightarrow \text{Native EAL Tool}.
\end{aligned}
$$

### Coverage

For each EAL-Bench domain, the registered design gives the number of selected ordinary trials and the authorized denominator per condition. Within each domain, the cases, seeds, writers, executors, and conditions in the registered design determine which trials enter the count. In the public design snapshot dated 18 September 2026, the request authorization field records the oracle decision for each request. The action field records whether the requested action occurred. In fact, the executor identifier names only the model. ### Important limitation

For a paired comparison of native and protected trials, both trial records must refer to the same request and the same frozen memory. However, the public benchmark archive omits the required trial records and frozen memories. Thus, the archive cannot establish how often the protected path permitted an unauthorized action. To assess coverage of the registered design, the [offline check](../Data_and_Code_Availability/S8_external_validation/eal_preflight_report.json) counts the ordinary trials specified for each domain.

## S8.3 AgentDojo

In AgentDojo, the legitimate user task determines the frozen legitimate support set before the authorization gate examines a consequential tool call. Under the [reviewed tool policy](../Data_and_Code_Availability/S8_external_validation/agentdojo_tool_policy_v1.json), the guard covers four suites, namely, Banking, Workspace, Slack, and Travel. In strict mode, the guard denies unclassified tools. Immediately before the native tool executes, the guard compares the proposed tool name and arguments with the calls in the legitimate task’s frozen reference set. Prompt-injected instructions form part of the context in which the agent proposes a tool. Thus, those instructions can affect the proposal, but they cannot authorize execution.

## S8.4 Agent Security Bench

For ASB, three conditions determine whether the available record for a case supplies primary evidence for the assessment of authorization consistency. Under the first condition, the record must identify the legitimate support against which the consequential action can be assessed ($C_1$). Under the second condition, the evidence must allow the consequential action selected by the attacker to be mapped to the legitimate support set ($C_2$). Under the third condition, the record must provide explicit evidence of the external effect produced by the consequential action under assessment ($C_3$). For a case to qualify for the primary analysis, the above conditions apply together as follows.

$$
\mathrm{Eligible}_{ASB}=C_1\land C_2\land C_3.
$$

For each ASB case, the [offline check](../Data_and_Code_Availability/S8_external_validation/asb_preflight_report.json) retains the native attack-success outcome and distinguishes it from evidence of an authorization violation. However, the native outcome alone cannot establish an external effect. This is because the native checker derives its outcome from messages. In addition, poisoned memory can influence how the agent selects a proposed action, but it cannot authorize execution. Thus, a native outcome supports a claim about an authorization violation only when the record meets the above conditions.
