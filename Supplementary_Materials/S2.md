# S2. Reference Implementation and Execution Invariants

## S2.1 Algorithm 1: Current Authorization Support Resolution

To determine whether a proposed action has current authorization, the resolver checks its support against the authority ledger and the durable execution state. First, the resolver selects eligible authority-bearing events for the requesting agent and the action. Next, the resolver builds the authorization graph from authenticated parent relations and locates the requesting agent’s terminal events with capabilities that support the action. Then, the resolver searches backward from those events toward an accepted root. Afterward, the resolver denies authorization if the search finds no valid support. Finally, if the search succeeds, the resolver reconstructs the candidate supports, selects one, and then returns it with the authorization decision. For the above graph search, the pseudocode and the expression for its expected complexity are as follows.

```text
Input:
    requesting agent A
    proposed action a
    current time t
    authority ledger L_t
    durable execution state E_t
    execution context ξ

Output:
    authorization decision Auth
    selected support S*

1.  V_t ← ∅
2.  Λ_t ← ∅
3.  Obtain authority-bearing events relevant to A and a
4.  For each event e:
        reject if unauthenticated, expired, revoked, or budget-ineligible
        otherwise add e to V_t
5.  For each authenticated parent relation e_i → e_j:
        require e_i,e_j ∈ V_t
        require Parent(e_j)=e_i
        require κ_j ⪯ κ_i
        add (e_i,e_j) to Λ_t
6.  G_t ← (V_t,Λ_t)
7.  Identify terminal events assigned to A whose capability supports a
8.  Search backward toward accepted roots
9.  If no root-connected valid support exists:
        return false, ∅
10. Reconstruct candidate supports
11. S* ← SelectSupport(candidate supports)
12. return true, S*
```

$$
O(|V_t|+|\Lambda_t|).
$$

## S2.2 Algorithm 2: Persistent Memory Revalidation

For each memory object, the system records the status of its authorization references without changing its informational content. First, the system prepares four sets, namely, current, historical, exhausted, and pending references. Next, the system checks each reference against current trusted state and places it in the corresponding set. Then, the system retains the information already present in the object. Afterward, it attaches the status labels to the retained content. Finally, the system returns the revalidated object as contextual information, but even a current reference cannot authorize the proposed action. For references that are missing, expired, revoked, exhausted, or temporarily reserved, the revalidation procedure assigns the status labels as follows.

```text
Input:
    memory object m
    time t
    authority ledger L_t
    durable state E_t

Output:
    revalidated memory object m*

1. CurrentRefs ← ∅
2. HistoricalRefs ← ∅
3. ExhaustedRefs ← ∅
4. PendingRefs ← ∅
5. For each authorization reference ref in m:
       e ← Resolve(ref,L_t)
       if missing / unauthenticated / expired / revoked:
           HistoricalRefs ← HistoricalRefs ∪ {ref}
       else if permanently exhausted:
           ExhaustedRefs ← ExhaustedRefs ∪ {ref}
       else if temporarily reserved by another execution:
           PendingRefs ← PendingRefs ∪ {ref}
       else:
           CurrentRefs ← CurrentRefs ∪ {ref}
6. Preserve informational content
7. Attach current status labels
8. return m*
```

## S2.3 Risk-treatment rule

For an action that passes deterministic authorization, the risk model uses the features of that action to compute the score for risk treatment. In fact, the score ranges from zero to one. Within the authorized action space, the available treatments include Allow, Constrain, Sandbox, and HumanVerify. If HumanVerify creates new authority, the system must append the authorization event to $L_t$ and then restart deterministic authorization. For an action with current authorization, the relation between its features and the bounded risk score is as follows.

$$
r_t=f_\phi(x_t),\qquad 0\le r_t\le1.
$$

## S2.4 Algorithm 3: Authorization-Consistent Protected Execution

First, the system revalidates the relevant memory, resolves current authorization, and then denies the proposed action if the authorization check fails. Next, the system applies the risk treatment within the grant and binds the selected support to a durable execution record unless new authority requires a restart. Then, the protected commit transaction revalidates the exact action and bound support, atomically reserves the required bounded authority, and revalidates the bound support for the same execution. Afterward, the system freezes the operation, records pending dispatch durably, commits the protected transaction, and then invokes the frozen operation. Finally, the system records confirmed success and confirmed absence of an external effect as committed and aborted, respectively. An uncertain outcome keeps the budget occupied and requires reconciliation before replay. For protected execution, the pseudocode specifies the order of these operations and the conditions for restarting authorization as follows.

```text
Input:
    agent A
    action a
    relevant memory M
    L_t, E_t
    risk model f_φ
    risk thresholds

1.  Revalidate relevant memory objects
2.  Auth,S* ← ResolveCurrentSupport(A,a,current_time,L_t,E_t,⊥)
3.  if Auth=false:
        deny
4.  r ← f_φ(ExtractRiskFeatures())
5.  Treatment ← RiskTreatment(r)
6.  Apply treatment only inside the already authorized action space
7.  If HumanVerify creates new authority:
        append trusted event
        restart deterministic authorization
8.  Create durable execution record ξ
9.  Bind S^ξ ← S*
10. Begin protected commit transaction
11. Revalidate exact action a and exact support S^ξ
12. Atomically reserve bounded authority required by S^ξ
13. If reservation fails:
        rollback reversible changes
        restart authorization
14. Revalidate S^ξ using execution context ξ
15. If S^ξ invalid:
        rollback reversible reservations
        restart authorization
16. Freeze action, target, arguments, S^ξ, operation ID, risk treatment
17. Persist status = dispatch pending
18. Commit protected transaction
19. t_c ← protected commit boundary
20. Invoke frozen external operation
21. if success confirmed:
        status ← committed
22. else if no external effect confirmed:
        status ← aborted
        release reversible occupied budget
23. else:
        status ← indeterminate
        retain occupied budget
        require reconciliation before replay
```

## S2.5 Runtime invariants

During protected execution, the runtime and its benchmark adapter must preserve the distinction between memory and execution authority. A memory reference supplies context. The runtime binds the exact support to a particular execution. For bounded authority, the system uses the same execution for reservation and protected commit, and an uncertain outcome alone cannot release the occupied budget. In addition, risk processing remains within the existing grant. For the above procedures, the runtime invariants are as follows.

1. *Memory:* During execution, the system can use memory as context, but a proposed action must obtain its execution authority independently of memory.
2. *Support binding:* For each execution, the system binds the exact support selected for that execution.
3. *Execution identifier:* The system uses one execution identifier for both reservation and commit.
4. *Protected commit:* At the protected boundary, the system revalidates the exact action together with the exact support bound to that execution.
5. *Bounded authority:* If an external invocation fails or its outcome remains uncertain, that outcome alone cannot justify the release of bounded authority.
6. *Risk treatment:* Within the authorized action set, risk processing can only narrow the set or impose additional treatment on an action already in the set.
7. *Adapter ordering:* To change the order of contextual annotation and support resolution, the benchmark adapter must preserve the independence of the trusted authorization decision from memory content.
