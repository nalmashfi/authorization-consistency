# S2. Algorithm Pseudocode and Execution Invariants

## S2.1 Algorithm 1: Current Authorization Support Resolution

For the requesting agent and the proposed action, Algorithm 1 uses the ledger and durable execution state to determine whether a valid support exists. First, the resolver selects eligible authority-bearing events. Next, it admits authenticated parent relations that satisfy capability narrowing and identifies eligible terminal events whose capabilities cover the proposed action. Then, from each terminal that meets these conditions, the resolver follows valid parent relations backward in search of a path to an accepted root. If the search reaches no accepted root, the resolver denies authorization because no path supplies valid support for the proposed action. Finally, a successful search lets the resolver reconstruct candidate supports, select one, and return it with the authorization decision. For the graph formed by eligible events and their valid parent relations, the search procedure and its time bound are as follows.

```text
Input:
    requesting agent A
    proposed action a
    current time t
    authority ledger L_t
    durable execution state E_t
    execution context ξ

Output:
    authorization decision Auth
    selected support S*

1.  V_t ← ∅
2.  Λ_t ← ∅
3.  Obtain authority-bearing events relevant to A and a
4.  For each event e:
        reject if unauthenticated, expired, revoked, or budget-ineligible
        otherwise add e to V_t
5.  For each authenticated parent relation e_i → e_j:
        require e_i,e_j ∈ V_t
        require Parent(e_j)=e_i
        require κ_j ⪯ κ_i
        add (e_i,e_j) to Λ_t
6.  G_t ← (V_t,Λ_t)
7.  Identify terminal events assigned to A whose capability supports a
8.  Search backward toward accepted roots
9.  If no root-connected valid support exists:
        return false, ∅
10. Reconstruct candidate supports
11. S* ← SelectSupport(candidate supports)
12. return true, S*
```

$$
O(|V_t|+|\Lambda_t|).
$$

## S2.2 Algorithm 2: Persistent Memory Revalidation

In Algorithm 2, revalidation assigns a status to each authorization reference while preserving the information that the agent retrieved from memory. First, the system initializes four sets, namely, current, historical, exhausted, and pending references. Next, the system uses the ledger to resolve the event for each reference and checks that event against the current trusted state. Then, the system retains the recorded contents of the memory object, attaches the assigned label to each reference, and finally returns the revalidated object. A current reference supplies context alone. For each reference, the system distinguishes historical, exhausted, pending, and current status using the conditions given as follows.

```text
Input:
    memory object m
    time t
    authority ledger L_t
    durable state E_t

Output:
    revalidated memory object m*

1. CurrentRefs ← ∅
2. HistoricalRefs ← ∅
3. ExhaustedRefs ← ∅
4. PendingRefs ← ∅
5. For each authorization reference ref in m:
       e ← Resolve(ref,L_t)
       if missing / unauthenticated / expired / revoked:
           HistoricalRefs ← HistoricalRefs ∪ {ref}
       else if permanently exhausted:
           ExhaustedRefs ← ExhaustedRefs ∪ {ref}
       else if temporarily reserved by another execution:
           PendingRefs ← PendingRefs ∪ {ref}
       else:
           CurrentRefs ← CurrentRefs ∪ {ref}
6. Preserve the information recorded in m
7. Attach the assigned status label to each reference
8. return m*
```

## S2.3 Risk-treatment rule

After an action passes deterministic authorization, the risk model computes its score from the features of that action. The score lies between zero and one. Within the scope of the grant, the system uses the thresholds to select the treatment for the proposed action from Allow, Constrain, Sandbox, and HumanVerify. If human verification provides additional authority, the system must record a new authenticated event in $L_t$ and then repeat deterministic authorization. For the runtime feature vector of an action that has passed deterministic authorization, the model computes the bounded risk score as follows.

$$
r_t=f_\phi(x_t),\qquad 0\le r_t\le1.
$$

## S2.4 Algorithm 3: Authorization-Consistent Protected Execution

In Algorithm 3, the system revalidates memory and resolves current support before applying risk treatment to an authorized action. If authorization fails, the system denies the action. Next, it binds the selected support to a durable execution record unless additional authority from human verification requires a new decision. Then, within one protected transaction, it revalidates the action and bound support, atomically reserves the required units, and checks the bound support for the same execution. Afterward, it freezes the operation, durably records pending dispatch, and commits before invoking the frozen operation with its durable identifier. Finally, the system records confirmed success, confirmed absence of an effect, or an uncertain outcome as committed, aborted, or indeterminate, respectively. The corresponding budget and replay rules are as follows.

```text
Input:
    agent A
    action a
    relevant memory M
    L_t, E_t
    risk model f_φ
    risk thresholds

Output:
    execution outcome

1.  Revalidate relevant memory objects
2.  Auth,S* ← ResolveCurrentSupport(A,a,current_time,L_t,E_t,⊥)
3.  if Auth=false:
        return authorization denied
4.  r ← f_φ(ExtractRiskFeatures())
5.  Treatment ← RiskTreatment(r)
6.  Apply treatment only inside the already authorized action space
7.  If HumanVerify creates new authority:
        record a new authenticated event in L_t
        restart deterministic authorization
8.  Create durable execution record ξ
9.  Bind S^ξ ← S*
10. Begin protected commit transaction
11. Revalidate exact action a and exact support S^ξ
12. Atomically reserve bounded authority required by S^ξ
13. If reservation fails:
        rollback reversible changes
        restart authorization
14. Revalidate S^ξ using execution context ξ
15. If S^ξ invalid:
        rollback reversible reservations
        restart authorization
16. Freeze action, target, arguments, S^ξ, operation ID, risk treatment
17. Persist status = dispatch pending
18. Commit protected transaction and record t_c
19. Invoke frozen external operation using the durable operation ID
20. if success confirmed:
        status ← committed
21. else if no external effect confirmed:
        status ← aborted
        release reversible occupied budget
22. else:
        status ← indeterminate
        retain occupied budget
        require reconciliation before replay
23. return execution outcome
```

## S2.5 Runtime invariants

During execution, both the runtime and the benchmark adapter must preserve the distinction between memory content and the trusted state used for authorization. A reference in memory supplies context. For a bounded grant, the execution must own its reservation at protected commit, and an uncertain outcome alone cannot release the occupied units. For an action admitted by deterministic authorization, the risk layer can restrict its execution only within the scope of the existing grant. Thus, the invariants governing the authorization decision, the protected execution, and the order of operations in the benchmark adapter are as follows.

1. *Memory:* During execution, the system can use memory as context, but a proposed action must obtain its execution authority independently of memory.
2. *Support binding:* For each execution, the system binds the exact support selected for that execution.
3. *Execution identifier:* The system uses one execution identifier for both reservation and commit.
4. *Protected commit:* At the protected boundary, the system revalidates the exact action together with the exact support bound to that execution.
5. *Bounded authority:* If an external invocation fails or its outcome remains uncertain, that outcome alone cannot justify the release of bounded authority.
6. *Risk treatment:* Within the authorized action set, risk processing can only narrow the set or impose additional treatment on an action already in the set.
7. *Adapter ordering:* To change the order of contextual annotation and support resolution, the benchmark adapter must preserve the independence of the trusted authorization decision from memory content.
