# S1. Formal Definitions and Supplementary Proofs

## S1.1 Trusted and contextual state

For a fixed action, the proposed model determines execution authority from the authenticated authority event ledger and the durable execution and effect state. Their symbols are $L_t$ and $E_t$, respectively. During a session, persistent memory $M_t$ and local session or checkpoint state $K_t$ can inform the action the agent proposes. Under complete mediation, each consequential external action must pass through the protected boundary, and the model assumes that changes to either component of trusted state cannot escape detection. Thus, the distinction between trusted authorization state and contextual state at time $t$ is as follows.

$$
\Omega_t^{auth}=\langle L_t,E_t\rangle,
$$

$$
\Omega_t^{ctx}=\langle M_t,K_t\rangle,
$$

$$
\Omega_t^{ctx}\not\Rightarrow\Omega_t^{auth}.
$$

## S1.2 Authority capability

For each grant, the authority capability identifies the authorized goal and sets the conditions under which the grant can be used. For the authorized goal $g$, the capability defines two sets, namely, the permitted operations and the resources they cover. The corresponding symbols are $\mathcal O$ and $\mathcal R$, respectively. In addition, $\Gamma$ gives the restrictions that apply when the capability is used, while $\tau$ and $b$ specify its validity interval and usage budget, respectively. For a narrowing from $\kappa_i$ to $\kappa_j$, the capability and the ordering that relates the original and narrowed capabilities are as follows.

$$
\kappa=\langle g,\mathcal O,\mathcal R,\Gamma,\tau,b\rangle,
$$

$$
\kappa_j\preceq\kappa_i.
$$

## S1.3 Trusted authority event

For each authenticated event, the ledger records the issuer, subject, capability, and the operation that the issuer performed. The identifier distinguishes events within the ledger. In addition, the record gives the parent event, time, and signature for a grant, delegate, narrow, renew, or revoke operation. A revocation enters the trusted history, but the revocation event itself carries no authority to execute an action. For an event indexed by $i$, the model groups the event identifier and the authenticated fields of the record as follows.

$$
e_i=
\langle
id_i,type_i,issuer_i,subject_i,\kappa_i,parent_i,t_i,\sigma_i
\rangle.
$$

## S1.4 Durable execution record

When the resolver selects a support for an action, the system binds that support to a durable execution record. The binding survives restoration of a contextual checkpoint. Within the durable execution record, the status field takes one of five values, namely, reserved, dispatch pending, committed, aborted, or indeterminate. For the execution indexed by $j$, the identifier, action, bound support, status, time, and result appear as follows.

$$
\xi_j=
\langle
id_j,a_j,S_j,status_j,t_j,result_j
\rangle.
$$

## S1.5 Bounded authority

For an authority event $e$, the system counts committed, reserved, dispatch-pending, and indeterminate units against the grant budget. A new reservation requires $\mathrm{Remaining}(e,t)>0$. For an execution that already owns a reservation, the reserved units remain available to that execution even when the grant has no units left for another reservation. Thus, at time $t$, the system obtains the units remaining for a new reservation by subtracting all occupied units from the event budget as follows.

$$
\mathrm{Occupied}(e,t)
=
N_{committed}
+
N_{reserved}
+
N_{dispatch}
+
N_{indeterminate},
$$

$$
\mathrm{Remaining}(e,t)
=
b_e-\mathrm{Occupied}(e,t).
$$

## S1.6 Authorization support

For a new authorization query, the proposed model tests whether an event sequence gives the requesting agent valid support for the action at the time of the query. One valid support suffices. For an execution with existing reservations, the model evaluates membership in $\mathcal S_t^\xi(a)$ using the units already reserved for that execution. Thus, the event sequence, the support family for a new query, and the authorization decision for that query are as follows.

$$
S=(e_0,e_1,\ldots,e_k).
$$

$$
\mathcal S_t(a)
=
\{S:\mathrm{Valid}(S,a,t,\bot)=1\},
$$

$$
AC(a,t)=1
\iff
\mathcal S_t(a)\neq\varnothing.
$$

## S1.7 Authorization graph

For a proposed action, the resolver admits an authority-bearing event to $V_t$ only if the event is authentic, current, and free of effective revocation. For a bounded grant, eligibility also requires the execution context to permit the agent to use the grant for the proposed action. An effective revocation can therefore exclude a vertex. In $\Lambda_t$, the resolver retains an authenticated parent relation only when both events are eligible and the child capability satisfies the narrowing condition. Thus, the graph and the time bound for finding a valid support if one exists are as follows.

$$
G_t=(V_t,\Lambda_t),
$$

$$
O(|V_t|+|\Lambda_t|).
$$

## S1.8 Persistent-memory rule

When an agent retrieves a persistent memory object $m$, it can use the stored information to select an action for the current session. A memory object supplies no execution authority. For example, an accurate record can describe a grant that has expired since the system wrote the record. Thus, current authorization and validity at use time remain subject to the restrictions on retrieval and recorded authority given as follows.

$$
\mathrm{Authority}(m)=\varnothing,
\qquad
\mathrm{Retrieve}(m)\not\Rightarrow\mathrm{Authorize}(a,t).
$$

$$
\mathrm{ValidAtWrite}(m)
\not\Rightarrow
\mathrm{ValidAtUse}(m).
$$

## S1.9 Restoration rule

When the system restores a checkpoint, the agent recovers the context recorded in that checkpoint and can use it to resume the earlier task. The current ledger and durable execution state remain in force. In particular, restoration cannot reverse a revocation, return consumed units to the budget, or release units held by reserved, dispatch-pending, committed, or indeterminate executions. Thus, the relation between restoration of an earlier context and rollback of current trusted authorization state is as follows.

$$
\mathrm{Restore}(K_{t_0})
\not\Rightarrow
\mathrm{Rollback}(L_t,E_t).
$$

## S1.10 Exact support binding

For each authorized execution, the system records the support $S^\ast$ selected by the resolver in the durable record for execution $\xi$. The notation $S^\xi$ identifies the bound support. If that support loses validity before protected commit, using an independent valid support requires a new authorization decision and, where appropriate, release of reversible reservations. Thus, the binding established by reservation and the restriction it places on subsequent commit are as follows.

$$
S^\xi=S^\ast.
$$

$$
\mathrm{Reserve}(S_1)
\not\Rightarrow
\mathrm{Commit}(S_2).
$$

## S1.11 Central protected-commit invariant

At protected commit, the system makes its last mediated check before the consequential operation enters the external subsystem. The check concerns the frozen action and its bound support. Although another support can authorize the same action, an execution cannot commit through that support using its existing reservation. Thus, the exact support must belong to the support family for that execution immediately before commit, as follows.

$$
\mathrm{ProtectedCommit}(a,\xi,t_c)=1
\Rightarrow
S^\xi\in\mathcal S^\xi_{t_c^-}(a).
$$

## S1.12 Supplementary proof arguments

In this section, the proof arguments establish how capability, authorization support, and protected execution determine the authorization properties of the proposed model. The lemmas establish capability monotonicity and graph reachability. For a fixed action, the subsequent proofs address changes of context and the effect of revoking an authority event. For bounded authority, the arguments examine competing reservations and the status of occupied authority after checkpoint restoration. Finally, the closing arguments cover cross-session authorization, the conditions at protected commit, and the limits of risk treatment.

### Lemma 1. Capability Monotonicity

*Argument:* For a valid support $S=(e_0,\ldots,e_k)$, the capability bound follows from the narrowing relation on each authenticated parent edge from the root to the terminal event. At each edge, validity requires the authority conferred by the child capability to remain within the scope of the parent capability. The capability ordering is transitive. Thus, successive applications of the narrowing relation along the support give the bound on the terminal capability as follows.

$$
\kappa_k\preceq\kappa_{k-1}\preceq\cdots\preceq\kappa_0.
$$

### Lemma 2. Support and Graph Reachability Equivalence

*Argument:* In $G_t$, a valid support for an eligible terminal event corresponds to a path of valid parent relations from an accepted root. In one direction, the eligible events in the support form the vertices, while their authenticated parent relations form the edges. These edges connect the accepted root to the terminal event. For the converse, a path from an accepted root to the eligible terminal event supplies the event sequence. Thus, if all its authority-bearing vertices are eligible and its edges satisfy capability narrowing, the path gives a valid support.

### Theorem 1. Contextual State Nonauthority

*Argument:* For a fixed action $a$ in execution context $\xi$, trusted state determines which of the possible supports are valid when the resolver makes its decision. In particular, the ledger $L_t$ and the durable execution and effect state $E_t$ supply the trusted state from which those current supports derive. Context can change the action an agent proposes. However, neither persistent memory $M_t$ nor local session or checkpoint state $K_t$ contributes authority for the fixed action. Thus, when trusted state remains the same, changes to either contextual component preserve the authorization decision for that action.

### Theorem 2. Selective Revocation Consistency

*Argument:* For an effective revocation, the target set identifies the authority-bearing events that lose validity when the revocation takes effect. A support fails if any required event belongs to that set. For an independent path, the resolver checks whether the events on which that path depends still form a valid support for the action. Thus, revocation withdraws authority for the proposed action only when no path retains a valid support for it.

### Corollary 1. Persistent Revocation Closure

*Argument:* After an authority event is revoked, an agent can still retrieve a memory record or restore an earlier context. Neither operation restores the authority removed by revocation. If every path that authorized the action depended on the revoked event, the action loses its last remaining valid support. Thus, the action can regain authorization only when a new independent valid support becomes available for that action.

### Theorem 3. Bounded Authority Safety

*Argument:* At the protected state boundary, atomic reservation serializes competing requests for units that remain available under an authority event. Competing executions cannot both acquire the last available unit. For a reserved, dispatch-pending, committed, or indeterminate unit, the system continues to count that unit against the budget until an authoritative release condition holds. Thus, atomic reservation limits the number of occupied units to the budget of the authority event at the time of the check, as follows.

$$
\mathrm{Occupied}(e,t)\le b_e.
$$

### Corollary 2. Restore Nonresurrection

*Argument:* When a checkpoint restores contextual state, the current ledger $L_t$ and durable execution and effect state $E_t$ continue to govern the availability of authority. Exhausted authority remains unavailable. In addition, revocation remains in force and the same trusted state continues to govern committed or otherwise occupied authority. Thus, a restore cannot give an execution access to authority that the current trusted state still excludes or counts against the budget.

### Theorem 4. Cross-Session Authorization Safety

*Argument:* For a memory object written during an earlier session, the cross-session argument concerns an action that still had authorization when the object was written. By the time the agent retrieves the object in a new session, every support on which the earlier authorization depended can have lost validity. The object provides no independent support. Thus, if no valid support remains when the agent retrieves the object, its record of earlier authority cannot establish $AC(a,t)=1$.

### Theorem 5. Protected Commit Authorization Soundness

*Argument:* Within one atomic transaction, the system revalidates the exact action and its bound support and verifies ownership of all required bounded reservations. The execution must own every such reservation. Before recording dispatch durably, the system freezes the operation within the same transaction, so a failed check prevents protected commit. Thus, if protected commit succeeds, the exact support bound to the execution belongs to the family $\mathcal S^\xi_{t_c^-}(a)$ for the frozen action immediately before commit.

### Theorem 6. AI Non Elevation

*Argument:* For the artificial intelligence (AI) risk layer, the set of actions available for risk treatment depends on the outcome of deterministic authorization. The sets $A_t^{auth}$ and $A_t^{risk}$ denote the actions that satisfy deterministic authorization and those that remain eligible after risk treatment, respectively. Risk treatment follows deterministic authorization. In addition, the risk layer has no operation that can create a new authorization support or bypass the protected gate. Thus, the relation between the action sets before and after risk treatment is as follows.

$$
A_t^{risk}\subseteq A_t^{auth}.
$$
