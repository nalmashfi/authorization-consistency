# S1. Formal Definitions and Supplementary Proofs

## S1.1 Trusted and contextual state

In the proposed model, the agent draws on contextual state when deciding what action to propose, but only trusted authorization state supplies execution authority. The authenticated authority event ledger and the durable execution and effect state constitute trusted authorization state. The model denotes these components by $L_t$ and $E_t$, respectively. For contextual state, $M_t$ represents the information held in persistent memory, while $K_t$ represents local session or checkpoint state. Thus, at time $t$ the distinction between the state that informs a proposal and the state that authorizes execution is as follows.

$$
\Omega_t^{auth}=\langle L_t,E_t\rangle,
$$

$$
\Omega_t^{ctx}=\langle M_t,K_t\rangle,
$$

$$
\Omega_t^{ctx}\not\Rightarrow\Omega_t^{auth}.
$$

## S1.2 Authority capability

For each grant, the authority capability identifies the authorized goal and sets the conditions under which the grant can be used. For the authorized goal $g$, the capability defines two sets, namely, the permitted operations and the resources they cover. The corresponding symbols are $\mathcal O$ and $\mathcal R$, respectively. In addition, $\Gamma$ gives the restrictions that apply when the capability is used, while $\tau$ and $b$ specify its validity interval and usage budget, respectively. For a narrowing from $\kappa_i$ to $\kappa_j$, the capability and the ordering that relates the original and narrowed capabilities are as follows.

$$
\kappa=\langle g,\mathcal O,\mathcal R,\Gamma,\tau,b\rangle,
$$

$$
\kappa_j\preceq\kappa_i.
$$

## S1.3 Trusted authority event

In the authenticated authority event, the fields describe the change to a capability and identify the parties to that change. The identifier distinguishes the event. For the event type, the model permits a grant, delegate, narrow, renew, or revoke operation. In addition, the record identifies the issuer, subject, and capability, then gives the parent event, time, and signature. For the event indexed by $i$, these fields appear in the record as follows.

$$
e_i=
\langle
id_i,type_i,issuer_i,subject_i,\kappa_i,parent_i,t_i,\sigma_i
\rangle.
$$

## S1.4 Durable execution record

For each protected execution, the durable execution record identifies the action and the authorization support bound to that execution. In addition, it gives the execution identifier, time, and result. In the status field, the record identifies the execution as reserved, dispatch pending, committed, aborted, or indeterminate. Restoring an earlier context preserves the durable record. For an execution indexed by $j$, the record associates the action and its support with the execution status and result as follows.

$$
\xi_j=
\langle
id_j,a_j,S_j,status_j,t_j,result_j
\rangle,
$$

## S1.5 Bounded authority

For an authority event $e$, the system determines whether it can reserve authority for a new execution by examining the units that already occupy the event budget. To obtain the occupied budget, the system counts units that are committed, reserved, dispatch-pending, or indeterminate. The system then subtracts that total from the event budget. A new reservation requires $\mathrm{Remaining}(e,t)>0$. Thus, at time $t$ the occupied budget and the budget remaining for a new execution are as follows.

$$
\mathrm{Occupied}(e,t)
=
N_{committed}
+
N_{reserved}
+
N_{dispatch}
+
N_{indeterminate},
$$

$$
\mathrm{Remaining}(e,t)
=
b_e-\mathrm{Occupied}(e,t).
$$

## S1.6 Authorization support

For a proposed action, the authorization query tests whether a sequence of authority events provides valid support at the time of the query. At least one valid support is necessary and sufficient for authorization. When the execution already owns reservations for the action, the family of valid supports for that execution is $\mathcal S_t^\xi(a)$. For a new query, the event sequence, the corresponding family of valid supports, and the condition for authorization are as follows.

$$
S=(e_0,e_1,\ldots,e_k).
$$

$$
\mathcal S_t(a)
=
\{S:\mathrm{Valid}(S,a,t,\bot)=1\},
$$

$$
AC(a,t)=1
\iff
\mathcal S_t(a)\neq\varnothing.
$$

## S1.7 Authorization graph

At the time of an authorization query, the resolver uses an authorization graph to find current support for the proposed action. Only eligible authority-bearing events belong to the vertex set $V_t$. For the edge set $\Lambda_t$, the resolver retains the valid authenticated parent relations that link those eligible events. In terms of the sizes of these sets, the authorization graph and the expected complexity of support resolution are as follows.

$$
G_t=(V_t,\Lambda_t),
$$

$$
O(|V_t|+|\Lambda_t|).
$$

## S1.8 Persistent-memory rule

For a persistent memory object $m$, the model separates the information used to reason about a proposal from the authority required to execute it. During reasoning, retrieval makes the stored information available to the agent when it proposes an action. However, retrieval alone cannot authorize the action. This is because the memory object confers no execution authority. In addition, a record can satisfy the validity condition when the system writes it and fail that condition when the agent uses it. Thus, the restrictions on authorization by retrieval and on validity at the time of use are as follows.

$$
\mathrm{Authority}(m)=\varnothing,
\qquad
\mathrm{Retrieve}(m)\not\Rightarrow\mathrm{Authorize}(a,t).
$$

$$
\mathrm{ValidAtWrite}(m)
\not\Rightarrow
\mathrm{ValidAtUse}(m).
$$

## S1.9 Restoration rule

When the system restores a contextual checkpoint, the current ledger and the durable execution state continue to determine which authority is available. The checkpoint can restore earlier contextual state. However, the restoration cannot release authority that remains reserved, committed, or indeterminate, or make consumed or revoked authority available again. Thus, the relation between restoration of a contextual checkpoint and rollback of trusted authorization state is as follows.

$$
\mathrm{Restore}(K_{t_0})
\not\Rightarrow
\mathrm{Rollback}(L_t,E_t).
$$

## S1.10 Exact support binding

For a proposed action, the runtime resolver selects the authorization support $S^\ast$ that the system will bind to the execution. When the system creates its durable execution record $\xi$, it records the support selected by the runtime resolver. The symbol $S^\xi$ denotes that bound support. In fact, an execution that holds a reservation on one support cannot commit silently through another support on the strength of that reservation. Thus, the binding and the restriction on support substitution are as follows.

$$
S^\xi=S^\ast.
$$

$$
\mathrm{Reserve}(S_1)
\not\Rightarrow
\mathrm{Commit}(S_2).
$$

## S1.11 Central protected-commit invariant

At the protected commit boundary, the authorization decision depends on whether the exact support bound to the execution remains valid. Even if a different support remains valid for the same action, its presence does not establish that the bound support remains valid. Immediately before protected commit, the bound support must belong to the support family for the action and the execution in question. Thus, the authorization-consistency invariant of the proposed model applies to every protected commit as follows.

$$
\mathrm{ProtectedCommit}(a,\xi,t_c)=1
\Rightarrow
S^\xi\in\mathcal S^\xi_{t_c^-}(a).
$$

## S1.12 Supplementary proof arguments

In this section, the proof arguments establish how capability, authorization support, and protected execution determine the authorization properties of the proposed model. The opening lemmas establish the capability bound along a valid support and relate valid support to a path in the authorization graph. For a fixed action, the subsequent proofs address changes of context and the effect of revoking an authority event. For bounded authority, the arguments examine competing reservations and the status of occupied authority after checkpoint restoration. Finally, the closing arguments cover cross-session authorization, the conditions at protected commit, and the limits of risk treatment.

### Lemma 1. Capability Monotonicity

*Argument:* For a valid support $S=(e_0,\ldots,e_k)$, the capability bound follows from the narrowing relation on each authenticated parent edge from the root to the terminal event. At each edge, validity requires the child capability to satisfy that relation with its parent. The capability ordering is transitive. Thus, successive applications of the narrowing relation along the support give the bound on the terminal capability as follows.

$$
\kappa_k\preceq\kappa_{k-1}\preceq\cdots\preceq\kappa_0.
$$

### Lemma 2. Support and Graph Reachability Equivalence

*Argument:* In $G_t$, a valid support for an eligible terminal event corresponds to a path of valid parent relations from an accepted root. In one direction, the eligible events in the support form the vertices, while their authenticated parent relations form the edges. These edges connect the accepted root to the terminal event. For the converse, a path from an accepted root to the eligible terminal event supplies the event sequence. Thus, if all its authority-bearing vertices are eligible and its edges satisfy capability narrowing, the path gives a valid support.

### Theorem 1. Contextual State Nonauthority

*Argument:* For a fixed action $a$ in execution context $\xi$, trusted state determines which current supports enter the authorization decision. In particular, the ledger $L_t$ and the durable execution and effect state $E_t$ supply the trusted state from which those current supports derive. Context can change the action an agent proposes. However, neither persistent memory $M_t$ nor local session or checkpoint state $K_t$ contributes authority for the fixed action. Thus, when trusted state remains the same, changes to either contextual component preserve the authorization decision for that action.

### Theorem 2. Selective Revocation Consistency

*Argument:* When the system revokes an authority-bearing event, it invalidates exactly the supports that depend on that event. An independent support remains valid while its own conditions hold. This is because at least one valid support suffices for the authorization of the action under the support rule. Thus, revocation can change the authorization decision for the action only if the family contains no unaffected valid support.

### Corollary 1. Persistent Revocation Closure

*Argument:* After an authority event is revoked, an agent can still retrieve a memory record or restore an earlier context. Neither operation reconstructs the revoked trusted event. If all valid supports for the action depended on that event, its revocation removes every such support. Thus, the action can regain authorization only when a new independent valid support becomes available for that action.

### Theorem 3. Bounded Authority Safety

*Argument:* At the protected state boundary, atomic reservation serializes competing requests for units that remain available under an authority event. Competing executions cannot both acquire the last available unit. For a reserved, dispatch-pending, committed, or indeterminate unit, the system continues to count that unit against the budget until an authoritative release condition holds. Thus, the budget of the event bounds the occupied authority under atomic reservation as follows.

$$
\mathrm{Occupied}(e,t)\le b_e.
$$

### Corollary 2. Restore Nonresurrection

*Argument:* When a checkpoint restores contextual state, the current ledger $L_t$ and durable execution and effect state $E_t$ continue to govern the availability of authority. Exhausted authority remains unavailable. In addition, revocation remains in force and the same trusted state continues to govern committed or otherwise occupied authority. Thus, restoring the earlier context cannot make any of that authority available to an execution again.

### Theorem 4. Cross-Session Authorization Safety

*Argument:* For a memory object written during an earlier session, the cross-session argument concerns an action that still had authorization when the object was written. By the time the agent retrieves the object, all current supports for that action can be invalid. The object provides no independent support. Thus, once all current supports have lost validity, retrieval of the object cannot by itself reestablish $AC(a,t)=1$.

### Theorem 5. Protected Commit Authorization Soundness

*Argument:* Immediately before protected commit, the system revalidates the exact action and the exact authorization support bound to that execution. To satisfy the reservation condition, the execution must itself own any bounded reservations that the action requires. The operation must also be frozen and the dispatch state durably recorded. Thus, when the system performs protected commit under the above conditions, the support owned by the execution belongs to $\mathcal S^\xi_{t_c^-}(a)$.

### Theorem 6. AI Non Elevation

*Argument:* For the artificial intelligence (AI) risk layer, the set of actions available for risk treatment depends on the outcome of deterministic authorization. The sets $A_t^{auth}$ and $A_t^{risk}$ denote the actions that satisfy deterministic authorization and those that remain eligible after risk treatment, respectively. Risk treatment follows deterministic authorization. In addition, the risk layer has no operation that can create a new authorization support or bypass the protected gate. Thus, the relation between the action sets before and after risk treatment is as follows.

$$
A_t^{risk}\subseteq A_t^{auth}.
$$
